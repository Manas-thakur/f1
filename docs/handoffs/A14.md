The brief's test: *each drill must cause the failure, not simulate a mock of
it.* Honest column by column.

### The two places where I approximated, stated plainly

**1. `test_worker_restart.py` persists the dead worker's advice itself.**
`workers/session_worker._build_runtime` constructs `SessionFactory()` with no
`recorder_factory`, so an out-of-process session writes **no** decision, no
execution event and no outcome record. There is therefore nothing in the store
to invalidate after the process dies. The drill rebuilds the dead worker's own
`Recommendation` objects from its snapshot — byte for byte, from
`snapshot["recommendations"]` — and persists them through a real
`SessionRecorder`, standing in for the recorder the worker does not have. The
module docstring says this in its first paragraph. The gap is defect A14-10.

**2. `test_disk_quota.py` tests a guard that is mine, not the product's.**
`grep -rn quota apps/ packages/ workers/` finds **nothing**. There is no disk
budget anywhere in the application, so the architecture's *"Disk full -> stop
experiment jobs first, preserve operational evidence, then withdraw if
necessary"* is entirely unimplemented. I implemented it in
`scripts/afterlap_ops/quota.py` and wired it into `scripts/batch_worker_main.py`
— which is real: the packaged `batch` service genuinely refuses to claim work
over the ceiling. `POST /experiments` still admits a job with the disk full;
that hunk is A14-5, and the third stage ("withdraw") has no consumer at all.
So the drill proves the guard behaves as specified and that the batch worker
honours it. It does not prove the product does, because the product does not.

## 5. Health and metrics, verified against the specification

| Spec line | Verified? |
|---|---|
| "Liveness means process loop alive" | **Yes.** With `app.state.capabilities` emptied, `/health/live` answers 200 `live` and `/health/ready` answers 503 `not_ready` with `missing: contracts, numerics, storage`. |
| "Readiness means required rules/model/source/storage capabilities available" | **Partly.** `REQUIRED_FOR_READINESS = ("contracts", "numerics", "storage")` and each one is tested to produce a 503. **Rules, model and source are not in the required set** and readiness does not consider them. A genuinely unwritable storage root was measured (`check_storage` → `unavailable: artefact root not writable: [WinError 183]`) and that real measurement produces a 503. |
| "A healthy HTTP server with stale telemetry is not a ready decision system" | **No — and it cannot be demonstrated in this release.** See below. |
| "Report planner time separately from end-to-end observation age" | **Shape yes, values no.** `/metrics` has separate `planner_duration_ms` and `observation_age_s` blocks. Both are permanently empty: defect A14-2. |
| "Structured logs carry session/decision/request IDs; do not include credentials" | **Yes.** A real credential in a real log record's `extra` is stripped: `database_url` comes out redacted, and `db_password` / `authorization` keys are dropped entirely by `JsonFormatter`. `session_id` survives. |
| "Health transitions publish quality events to all clients" | **Not verified, and I believe not implemented.** No health-transition publisher exists; quality events are published by the session runtime for channel quality, not by the health endpoints. |

### The stale-telemetry line, in full

This is the most important negative finding in the health section, so it is
stated precisely rather than summarised.

1. **The freshness machinery is correct.** A real `QualityTracker` with a real
   20 Hz expectation, one observation, then elapsed time, classifies
   `valid → degraded → stale → missing` at ages 0.05, 0.15, 0.5 and 5.0 s. A
   transport heartbeat does **not** make a dead channel look alive.
2. **`/health/ready` never looks at telemetry at all.** It reads only the
   process-level doctor report captured once at startup. Defect A14-4.
3. **The simulator source cannot report stale.**
   `InProcessSessionRuntime.initialise` builds the source capability from
   `self._config.observation_rate_hz` — the same number that decides how often
   it delivers. Declared rate and delivered rate move together by
   construction. Configured at 0.05 Hz, the decision cutoff really does fall
   10.16 s behind the session clock, and every channel still reports
   `quality: valid` with `expected_period_s: 20.0` — correctly, because the
   source promised 20 s and delivered at 20 s. Limitation A14-9.

So: the acceptance case *"a healthy HTTP server with stale telemetry is not
ready"* is **not** satisfied, and with this observation source the condition is
not even reachable end to end. Both halves need work: A14-4 makes readiness
session-aware, A14-9 separates the declared rate from the delivery cadence so
the condition can be produced. Until both land, no claim should be made that
this behaviour is implemented. `test_the_simulator_source_declares_its_own_
delivery_rate_so_it_cannot_report_stale` asserts the limitation so it cannot
regress unnoticed, and its docstring tells whoever fixes it to replace the test
with a real end-to-end drill.

## 6. Defects found

Full hunks in `handoffs/A14-integration-patch.md`. Each of A14-1, -2, -4, -7
and -8 has an `xfail(strict=True)` drill.

| ID | Severity | One line |
|---|---|---|
| **A14-7** | **high** | `check_model_compatibility` ignores `approval_status`: an **unevaluated** bundle is enabled as a learned contribution on manifest agreement alone. `AGENTS.md` forbids automatic promotion. |
| **A14-8** | **high** | `SessionFactory` never passes `expected_feature_hash`, so the runtime calls the compatibility check with `None` and the **feature-manifest check never runs**. A bundle trained on a different observation encoding is accepted. |
| A14-1 | high | `OutboxPublisher.stop_running()` cancels with no final drain, so a lifecycle change committed after the last poll is never delivered. Graceful shutdown is a named acceptance case. |
| A14-2 | high | `observe_planner`, `observe_observation_age` and `spool_depth` have **no caller anywhere in `apps/`**. `/metrics` reports the required shape with `samples: 0` for the life of the process. |
| A14-3 | high | `runtime.mark_communicated()` is never called from the `mark_communicated` route, so `ExecutionEvent.delay_from_communication_s` is always `None` and **operator-to-execution delay is never measured** — a metric the spec names. |
| A14-4 | high | `/health/ready` ignores session health entirely. |
| A14-5 | medium | No disk-budget guard anywhere in the application; `POST /experiments` admits a job with the artefact root full, and the "withdraw" stage has no consumer. |
| A14-9 | medium | The simulator's declared observation rate is derived from its delivery cadence, so stale telemetry is unreachable. |
| A14-10 | medium | A spawned session worker builds its runtime with **no recorder** (persists nothing) and mints its **own session id**, so `WorkerConfig.session_id` and the runtime's identity disagree. |
| A14-11 | low | The instructed profile is not a wire field; recovering it means parsing `display_text` (which `scripts/demo.py` does, under protest) or offering the whole admissible set (which the console does). |

A14-7 and A14-8 compound: with both present, a bundle can be **loaded,
unapproved, against the wrong feature encoding** and still report
`learned_contribution_enabled: true` on a published recommendation. Individually
each is a missing check; together they remove the whole model-compatibility
gate. They are one-and-two-line fixes and should be first.

## 7. Measured performance

**Hardware and software.** Windows 11 Home Single Language 10.0.26200, Intel64
Family 6 Model 183 Stepping 1 (24 logical CPUs), CPython 3.12.14, numpy 2.5.3,
Docker 29.6.2 / Compose v5.3.1 on the WSL2 Linux backend
(`Linux-6.18.33.2-microsoft-standard-WSL2-x86_64`), overlayfs, PostgreSQL
17.7-alpine. Single-threaded application code, no profiling or optimisation
work.

### Cold start

| Measurement | Value |
|---|---|
| Application lifespan entered → `/health/ready` 200, empty artefact root, SQLite | **7.63 s** |
| `docker compose down -v` then `up -d --wait` to all-healthy, empty volumes | **13.41 s** |

The 7.63 s is dominated by `run_doctor`, which imports torch and solves a real
constrained OCP with IPOPT during startup. That is a deliberate design choice
(readiness is a measurement, not an assumption) with a measurable cost; it is
worth knowing before anyone sets a container `start-period` under 40 s. The
Dockerfile uses 40 s.

### Operator command path — and a large platform difference

Same code, same runbook, same scenario and seed.

| Measurement | Compose (Linux, PostgreSQL 17.7, via nginx) | Native (Windows, SQLite `synchronous=FULL`) |
|---|---|---|
| Demo runbook, 13 steps | **2.81 s**, 2.95 s | **159.44 s**, 149.69 s |
| `POST /commands` `kind=step`, p50 | **77 ms** (min 61, max 91, n=8) | **5 905 ms** (min 5 813, max 5 930, n=8) |

**77× on the operator command path**, and it is not physics: A08 measured
`advance(1.0 s of session time)` at about 56 ms in-process, which accounts for
most of the 77 ms container figure. The remaining ~5.85 s per step on the
native path is consistent with SQLite's fsync-per-commit on NTFS — a step
commits several rows (decision, outbox, session row) — but **that attribution
was not isolated further and must not be quoted as a measured cause.**

Two consequences:

1. **Nothing may be benchmarked on the native Windows/SQLite path.** Numbers
   from it are dominated by commit latency and say nothing about the product.
   The recommended local development command in the brief is that path.
2. The same runbook produced the **same snapshot hash** on both platforms
   (`sha256:eab94853b460759caf76c31cff1411a4687f1075ccf3a29ec4e2c8a52efdfd43`),
   so this scenario and seed are bit-reproducible across Windows and Linux.
   That is **one observation**, not a determinism proof.

### Images and bundle

| Measurement | Value |
|---|---|
| `afterlap/api:local` | 1.27 GB |
| `afterlap/web:local` | 101 MB |
| `tests/operations` suite | 156–164 s over four runs |

## 8. Assumptions and declared invented values

1. **`QuotaPolicy` defaults — 2 GiB experiment ceiling, 256 MiB operational
   reserve — are invented.** They are not derived from a measured artefact
   growth rate. `AFTERLAP_EXPERIMENT_QUOTA_BYTES` and
   `AFTERLAP_OPERATIONAL_RESERVE_BYTES` override them; a malformed value is an
   error, never a silent fall back to the default. The *ordering* (experiment
   output yields first) is specified; the numbers are placeholders and should
   be set from a measured session's growth once `MemorySink` is replaced
   (A08 §9.15).
2. **The quota's tree classification is a policy choice.**
   `trajectories/`, `reports/`, `objects/`, `staging/` are treated as
   recomputable; `spool/`, `exports/` and the database file are treated as
   evidence. An **unclassified** tree counts as evidence — the conservative
   direction, since it makes the guard trip sooner, never later. Asserted in
   `test_an_unclassified_tree_counts_as_evidence_not_as_experiment_output`.
3. **The batch runner resolves treatments by id**, because
   `ExperimentManifest` stores `treatment_ids` but not
   `TreatmentSpec.controller` (which exists only in the request body). Two ids
   resolve (`legal_fixed_schedule`, `legal_greedy_attacker`); anything else
   becomes an `UnavailableController` — an explicit unmeasured row, never a
   substituted controller.
4. **The batch runner does not branch from the snapshot.** Each unit starts
   from the frozen scenario and seed, not from the operator's branch point.
   The snapshot hash is carried into the report so the mismatch is visible, and
   the report's own `limitations` list says so. Also labelled
   `split="tuning"`, never `"test"`: opening the held-out split is a visible
   promotion act, not a queued job.
5. **`source_revision` is a content digest, not a commit id.** No git command
   was run and the enclosing repository was not read. The manifest records
   `kind: content_digest`.
6. **"Approved rules" in the bundle means loadable and hashed.** No FIA
   document has been resolved against any pack; the section detail says exactly
   that.
7. **Ports 8080 / 8010 / 5433** were chosen to avoid a collision with a
   native dev server on 8000 and existing PostgreSQL containers on 5432 and
   32900 on this machine. They are `.env` variables, not constants.
8. **The demo script reads the instructed profile out of `display_text`.**
   That is the only place it is available on the wire (A14-11). The helper
   validates the token against `DeploymentProfile` **and** against
   `rule_context.admissible_profiles` before using it, and fails loudly rather
   than guessing.
9. Every scenario, car, track, rule pack and objective used here is the
   repository's own **synthetic** fixture. The credential in
   `test_security.py` (`n0t-a-real-password-Ku3Rr7x`) and the compose password
   used for the drills (`drill-only-not-a-real-secret`) are invented test
   values for a database that only ever ran on loopback; neither is a real
   secret and neither is in `infra/.env` (which does not exist in the tree).
   No external dataset, no licensed feed, no network access outside `uv` and
   `pnpm` package downloads during the image builds and `docker pull` of the
   five base images.

## 9. Known limitations

1. **The disk-quota guard is in `scripts/`, not in the product.** It is real,
   tested and used by the packaged batch worker, but `POST /experiments` does
   not consult it and no session withdraws on `QuotaVerdict.WITHDRAW`. The
   module has no dependency beyond `os`, `shutil` and `pathlib` and should move
   to `packages/core/afterlap_core/quota.py` (A14-5); I may not create a
   `packages/core/` module.
2. **`tests/operations/conftest.py` duplicates a small session helper**
   already in `tests/backend/conftest.py`. `tests/` is not a Python package so
   `tests.backend.conftest` is not importable, and a path hack into another
   worker's suite would be worse. If the coordinator adds `tests/__init__.py`,
   the two should be merged.
3. **`scripts/` is not a workspace member.** `afterlap_ops` is imported by
   putting `scripts/` on `sys.path` (once, in the conftest). Fine for
   operations code; it would not be fine for anything the application imports.
4. **No second host.** Both images built and ran here. No pull-and-run from a
   registry on a different machine has been attempted, and both image builds
   need network access for `uv` and `pnpm`.
5. **No TLS, no authentication, no roles, no private network policy.**
   `AFTERLAP_ENV=production` disables the development bootstrap operator, which
   in this release means nobody can operate a session at all. That refusal is
   correct and it is why `development` on loopback is the only supported mode.
6. **The release bundle's self-sufficiency check is partial.** Configs,
   scenarios, rules, tracks, cars and objectives were verified to resolve from
   the bundle's own `source/` tree, and a session ran to an actionable
   instruction from them. Not verified: a from-scratch `uv sync --frozen` and
   `pnpm install --frozen-lockfile` inside the bundle on a machine with no
   existing environment.
7. **`deploy.resources.limits.cpus` on `batch` is a ceiling, not a
   reservation.** `ARCHITECTURE.md` asks that batch work cannot consume the
   runtime's reserved cores. Under contention the API still competes. Doing it
   properly needs `cpuset` pinning, which depends on the host's core count.
8. **The `batch` service has no healthcheck.** It inherits the API image's,
   which probes an HTTP endpoint it does not serve, so it is explicitly
   disabled. Compose therefore cannot tell you the batch worker has wedged. A
   real check would read its lease heartbeat.
9. **`docker compose down -v` deletes the audit trail.** There is no backup
   step in this packaging and no `pg_dump` sidecar, while the bundle's
   `ROLLBACK.md` assumes the database survives a rollback.
10. **SQLite write contention appears in the drill logs.** Several drills log
    `sqlite3.OperationalError: database is locked` from
    `afterlap.session.publisher` while a session is stepping. It is handled —
    the publisher logs, retries on its next pass, and the outbox row stays
    unpublished until a drain succeeds, so nothing is lost — and it does not
    arise on PostgreSQL. Recorded so a reviewer seeing it knows it is
    understood, not ignored.
11. **acados is still not built.** Coordinator decision D-02 stands and
    `api.Dockerfile` says so in a comment. Building it from a pinned commit
    inside the Linux image is the obvious next packaging task and was not
    attempted here.
12. **The learning extra is excluded from the API image.** On Linux `torch`
    pulls the entire CUDA runtime. `doctor` inside the container reports torch
    and the learning stack as **degraded**, which is accurate, and readiness
    does not depend on either — but any containerised path that needs the
    learned contribution needs a second image that does not exist.
13. **Metrics coverage is thin even after A14-2.** Ingestion age by channel,
    clock uncertainty, queue depth, estimator residuals and coverage, planner
    candidate and rejection counts, rule-context unknown counts,
    recommendation expiry and churn, WebSocket resync count, database latency,
    failed-job count and model/version mismatch count are all named by the
    operations spec and none reaches `RequestMetrics`. Every one of them exists
    as a value in a tick or a repository row. A14-2 wires three; the rest is a
    larger piece of work listed in the patch file.
14. **`/metrics` is JSON, not the Prometheus text format**, despite
    `prometheus-client` being a declared dependency of `afterlap-api`. Nothing
    scrapes it today so nothing is broken, but a Prometheus scrape would need a
    second endpoint or a format change. Pre-existing, not introduced here.
15. **The health endpoints publish no quality event on transition**, which
    `operations/TECHNICAL_SPEC.md` asks for ("Health transitions publish
    quality events to all clients"). Not implemented and not attempted; it
    needs a health-transition detector that owns state across probes.
