## 2. The `Planner` protocol

```python
@runtime_checkable
class Planner(Protocol):
    @property
    def identity(self) -> str: ...
    def plan(self, request: PlanRequest) -> PlanningResult: ...


@dataclass(frozen=True, slots=True)
class PlanRequest:
    session_id: str
    revision: int  # the runtime revision this request was issued against
    now_s: float
    deadline_s: float
    estimate: StateEstimate
    rule_context: RuleContext
    manifest: RuleManifest  # the pack the context was resolved from
    checker_state: CheckerState  # A04's reintegration state
    objective_version: str
    admissible: tuple[DeploymentProfile, ...]
    model_hash: str | None = None
    learned_contribution_enabled: bool = False
    baseline_identity: str = BASELINE_IDENTITY
    segment_length_m: float = 600.0
    lead_time_s: float = 1.2
    execution_window_s: float = 1.5
    horizon_s: float = 20.0
    notes: tuple[str, ...] = ()
```

Rules a planner must satisfy, all of which the runtime enforces afterwards:

* return a `PlanningResult` whose `state_revision == request.revision`; the
  runtime discards a result whose revision no longer matches (`accept_plan_result`
  → `PlanApplication.discarded`);
* never raise for an ordinary refusal — return a non-`OK` status with reason codes;
* `harvest_target_j` is **battery energy gain** and `requested_budget_j` is energy
  leaving the battery (coordinator decision D-01);
* the `constraint_result` on a returned candidate is a draft. The runtime always
  overwrites it with `rules.check_plan(..., manifest=pack.manifest)` and publishes
  only a `PASS`.

`default_planner() -> (Planner, str)` prefers `afterlap_core.planning.plan` when
importable and falls back to `BaselinePlanner`, returning a note naming which
path was taken. **`SessionFactory` and every test use `BaselinePlanner`
explicitly**, so this module's suite does not depend on A06's in-flight state.
The `_ExternalPlannerAdapter` argument mapping is written against A06's current
signature and is **untested** — see §9.

## 3. How the loop closes

```
Simulator.step(dt=0.02 s)
  -> Simulator.observe()  [delayed 0.15 s, noisy, quantised, energy-gated]
  -> SimulatorObservationSource.offer()      # observation fields only
  -> SimulatorAdapter (A02)                  # find_truth_leaks on every record
  -> IngestionPipeline                       # dedup, reorder, SI, sequence, quality
  -> estimation.update(events, state, EstimationContext(cutoff_s=...))
  -> EligibilityMachine.advance(...)         # detection/activation crossings
  -> rules.resolve_pack_context(...)         # limits + admissible profiles
  -> degradation.assess(...)                 # every table row, one result each
  -> Planner.plan(PlanRequest(revision=...)) # discarded if the revision moved
  -> rules.check_plan(..., manifest=pack)    # the independent verdict
  -> Recommendation (PASS) or WITHDRAW_ADVICE
  -> SessionRecorder.publish_recommendation -> store_decision + outbox
  -> apply_operator_action(SELECT)           # selection is not execution
  -> apply_operator_action(MARK_COMMUNICATED)
  -> queue_driver_input(...)                 # + configured reaction delay
  -> ExecutionEvent, later, separate sequence -> record_execution -> EXECUTING
  -> Simulator.step(action)                  # the physics change
  -> next observation -> next estimate -> next decision
```

**Decision cutoff.** `cutoff_s` is the newest observation session time that
actually reached the estimator; `created_at_s` is the publication time and is
always ≥ the cutoff. `pipeline.finalise(cutoff_s)` is called when a decision is
published (A02's requested integration action), so a later arrival at or before
the cutoff is archived but excluded from the state that decision observed.
`test_vertical_slice` asserts that every `contributing_event_id` on the published
estimate has an observation time ≤ `cutoff_s`.

**Revision.** Monotonic, bumped on every mutation: `initialise`, each `advance`,
`decide_now`, `pause`/`resume`, a queued driver input, an emitted execution, a
rule-pack swap, an explicit invalidation and a restore. A `PlanRequest` carries
the revision it was issued against; `accept_plan_result` refuses to apply a
result whose revision no longer matches *and* a result whose own
`state_revision` disagrees with the request.

**Simulated driver execution.** `queue_driver_input` places a deliberate input
behind the scenario's own `reaction_delay_mean_s` (0.35 s for the shipped
scenario). No `ExecutionEvent` exists until that delay has elapsed in session
time; the event then arrives on a later tick with its own sequence,
`source=simulated`, and `delay_from_communication_s` measured from
`mark_communicated`. An input with no `recommendation_id` is recorded
`UNSOLICITED` with `recommendation_id=None` — an unmatched driver action is
evidence and is never forced onto a recommendation. `apply_driver_action` (the
port method the HTTP route calls) queues and then advances by exactly the
reaction delay so it can return the event synchronously; the event is still a
later event than the command.

**Expiry and invalidation between ticks.** Every decision cycle calls
`expire_due(session_id, session_time_s)` before anything else, so advice a
browser still shows cannot be acted on after its window closed.
`set_rule_pack` calls `invalidate_outstanding` and bumps the revision.

## 4. Truth isolation

`SimulatorObservationSource` never holds the simulator or a `WorldState`. The
runtime pushes one already-built `Observation` (a frozen dataclass of
observation fields) into `offer()`, which is A02's requested shape ("implement it
on a view object, not on the simulator itself").

Published channels are exactly what is published, and no more:

| Car | Vendor fields emitted |
|---|---|
| own | `speed_mps`, `progress_m`, `lap_distance_m`, `battery_temperature_k`, `gap_ahead_s`, `gap_behind_s`, and `battery_energy_j` **only when the scenario's `energy_channel_available` is true** |
| rival | `speed_mps`, and `progress_m` derived as own progress + observed relative progress |

`FORBIDDEN_RIVAL_FIELDS` (`battery_energy_j`, `battery_temperature_k`,
`recharge_this_lap_j`, `recharge_cumulative_j`) raise `TruthIsolationError` if a
rival mapping ever presents them, so a future `expose_rival_energy: true`
scenario cannot leak through this adapter by accident. `SimulatorAdapter`'s own
`find_truth_leaks` check runs on every record and is satisfied, not defeated.

An observation with no channels (nothing yet old enough to have been delivered)
emits **nothing**; it is counted on `source.skipped_missing` rather than filled
with zeroes. Draining `observations()` is destructive and the source refuses to
re-emit a source time it has already emitted, which is A02 requirement 6.

`test_vertical_slice` asserts on the serialised normalised records that no rival
record carries an energy or thermal channel and that the own car's energy is
observed while the rival's never is.

## 8. Assumptions and declared invented values

1. **Overtake gap threshold.** `synthetic-pack-v1` declares detection and
   activation line positions but **no gap threshold**, and does not list one as an
   unknown condition. A session must therefore state which threshold it is
   evaluating at the detection line. `SYNTHETIC_GAP_THRESHOLD` uses **1.0 s**,
   `provenance="synthetic_assumption"`, with a note saying no FIA document was
   resolved for it. `UNRESOLVED_GAP_THRESHOLD` is the alternative and yields
   `gap_condition_met=None`, which correctly leaves eligibility `UNKNOWN` and
   suppresses advice (`test_an_unresolved_gap_threshold_keeps_eligibility_unknown`).
   The policy and its provenance are written into `export_record()`.
2. **Unknown current electrical power is treated as 0 W for the power-ramp
   check only.** That is the conservative direction: it maximises the demanded
   change at entry, so an unknown current power can only make a plan look harder
   to execute, never easier. It is documented on `checker_state_for`.
3. **Analysis-only rule context.** With no measured energy channel the rule
   context still has to be resolved from *some* energy value. The runtime uses
   the lower bound of the reachable set (`conservative_energy_floor_j`), which can
   make a profile inadmissible but never admissible. It is never published as a
   value and never sizes a budget: the energy directive is withdrawn instead.
4. **Driver execution is modelled in two legs.** The runtime models the human
   leg (radio call → driver acts) with the scenario's `reaction_delay_mean_s`;
   the simulator then applies its own equal reaction delay before the profile
   becomes active in the world. Total latency from queue to physics is therefore
   about twice the configured delay. This is a modelling choice, stated, not
   calibrated against anything.
5. **Budget semantics follow D-01 and D-05.** `requested_budget_j` is energy
   leaving the battery and `harvest_target_j` is battery energy gain; the
   checker converts to the ERS-K and CU-K buses itself. Following D-05, the
   baseline planner compares its budget against the battery headroom directly
   and applies no discharge-efficiency factor of its own — the checker's two
   conversions cancel and the ledger drains exactly the requested joules.
6. **`BaselinePlanner`'s deploy/harvest fractions and its ranking heuristic are
   invented**, declared in the module, and are deliberately *not* the simulator's
   `DEPLOY_FRACTION` table: the two are allowed to disagree and the independent
   checker arbitrates. `SAFETY_MARGIN = 0.5` (half the distance to any bound) is
   what keeps the two integration models from disagreeing into an illegal plan.
7. **`debug_truth()` on the runtime.** `TECHNICAL_SPEC.md` keeps debug truth on a
   separately authorised path unavailable in replay and live-team modes. The
   runtime's accessor refuses outside a simulation session, is called by nothing
   on the publishing path, and no value it returns reaches a `StateEstimate`, a
   `Recommendation` or an export. It is used by tests only.
8. Every scenario, car, track, rule pack and objective used here is the
   repository's own **synthetic** fixture. No measured telemetry, no external
   data, no network access anywhere in this module or its tests.

## 9. Known limitations and defects

1. **The simulator publishes no `electrical_power_w` channel, and the cost is
   measurable.** `afterlap_core.simulation.observation.OWN_CHANNELS` has no
   electrical-power entry, so the capability does not claim one and A05's energy
   filter has no power observation to integrate. Measured on the shipped
   scenario, comparing the published estimate against hidden truth **at the
   estimate's own cutoff**: speed |err| mean 0.16 m/s (max 0.97), progress |err|
   mean 2.4 m, but **own energy |err| mean 87 kJ, p95 362 kJ, max 410 kJ** on a
   4 MJ window. The observed `battery_energy_j` channel is accurate to its 400 J
   quantisation; the filter simply corrects towards it with a very small gain
   (energy measurement sigma 15 kJ against a process sigma of ~200 J per 50 ms
   tick), so after a step change in deployment the estimate converges with a time
   constant of roughly 4 s. This is not a defect in this module — it is a missing
   channel — but the planner sizes energy budgets from that estimate, so it
   matters. See integration action §10.1. I have **not** derived a power channel
   from differenced battery energy: that is battery-side power, not DC-bus power,
   and A05 explicitly forbids deriving one ledger from another.
2. **`recharge_ledger_j` is not published either** (no vendor mapping entry
   exists for it), so `recharge_spent_this_lap_j` is always missing and the
   checker's per-lap recharge ledger always starts from zero within a session.
   On a multi-lap session this under-counts the allowance.
3. **Advice is suppressed for the first ~21 s of the shipped scenario.** A04's
   `_check_overtake_eligibility` returns `UNKNOWN` whenever
   `context.eligibility is UNKNOWN`, *before* it looks at whether the plan asks
   for an overtake at all. A plan requesting only HARVEST is therefore `UNKNOWN`
   until a detection line has been crossed. The runtime honours this and
   withdraws advice, which is the specified behaviour for an unknown critical
   constraint, but it means a fresh session issues nothing until 1 600 m have
   been covered. Worth a coordinator decision (§10.4).
4. **A06's planner adapter is untested and incomplete.** `default_planner()`
   will select it when `afterlap_core.planning` imports, but
   `_ExternalPlannerAdapter.plan` maps arguments against A06's published
   signature and nothing in this suite exercises it, and the runtime does not yet
   use A06's `build_recommendation` / `active_plan_from` pair (§10.5). The
   factory default is `BaselinePlanner`, so nothing silently depends on it.
5. **The runtime is in-process.** `SessionFactory` attaches
   `InProcessSessionRuntime`, so physics currently runs in the API process.
   `SessionWorkerHandle` spawns a real worker and is tested end to end, but the
   proxy that would implement `SessionRuntimePort` over the command queue is
   **not written**, so the API cannot yet drive an out-of-process session.
6. **No PostgreSQL run.** Everything is SQLite. `_lock_session`'s `FOR UPDATE`
   and `claim_experiment_job`'s `SKIP LOCKED` are no-ops there, so
   `test_concurrent_selections_...` proves the application-level guard plus
   SQLite's write lock, not the PostgreSQL row lock.
7. **`operator_action` outbox rows are never delivered.** They have no
   `StreamEventType`, so the publisher quarantines them, logs a
   `PublisherFault`, leaves `published_at` NULL and moves on. Nothing a client
   needs is lost (the accompanying `recommendation_updated` row carries the
   lifecycle change and the test asserts it arrives) but the rows accumulate.
   §10.2.
8. **`store_decision` and `record_execution` write an outbox payload without the
   discriminator** `StreamEnvelope` needs. The publisher repairs it by labelling
   the payload with the row's own `event_type` and nothing else — it adds,
   changes and guesses no value — but the repair path should not need to exist.
   §10.3.
9. **The estimate is not projected forward to the decision time.** The published
   posterior is at the cutoff, i.e. `delay_s` behind the simulator clock. A05's
   `predict()` is not used. The plan's lead distance absorbs the lag, but a plan
   is made against a state 0.15 s old and this is not compensated.
10. **`RuntimeConfig.observation_rate_hz` (20 Hz) is a configuration, not a
    measurement.** The simulator can supply it because it runs at 50 Hz, but the
    capability's declared rate must be changed together with the config or the
    quality tracker will mis-judge freshness.
11. **`OutboxPublisher.run` polls at 50 ms.** There is no event-driven wakeup, so
    a committed lifecycle change can sit undelivered for up to that interval.
12. **The spool's replay is all-or-stop.** `drain_spool` stops at the first entry
    that fails again and re-spools the remainder in order. It never skips ahead,
    which preserves ordering but means one permanently-bad entry blocks the rest.
13. **Cancellation of a *running* batch job is cooperative only.** The route
    records the terminal status; a worker that never checks its token is never
    interrupted. There is no watchdog.
14. **`_position()` and `_record_checkpoint_outcomes()` read the simulator's
    world** for the outcome record's position and checkpoint crossings. Those are
    realised-outcome facts recorded after the fact, not controller inputs, and
    nothing from them reaches an estimate or a plan — but it is a truth read on
    the runtime side and a reviewer should confirm the boundary is where they
    want it.
15. **The ingestion sink is `MemorySink` and grows without bound.** Every
    normalised telemetry record for the session stays in memory (measured: 5 584
    records in 34 s of session time, ~165/s, so a race-length session would hold
    close to a million). A02's `TelemetryRecorder` (Parquet chunks) or a
    `LosslessBuffer` should replace it before any long session is run. §10.10.
16. **The telemetry sequence space and the session event sequence space are
    separate, deliberately.** A02 asked for `IngestionRouter.sequences` to be
    wired into the session's stream sequence. It is not: the session sequence is
    allocated by `next_sequence()` on the `session` row, one per *lifecycle*
    event, while the ingestion allocator numbers telemetry samples at 160/s.
    Joining them would mean a database round trip per telemetry sample, which
    `PERSISTENCE_AND_WORKERS.md` explicitly rules out ("the database is not
    polled on every physics tick"). The consequence is that a client cannot
    detect a telemetry gap from the stream sequence alone. §10.11.
17. **No session badge is published.** A02's `badge_for(mode, counterfactual)`
    is not called; `SessionSnapshot` has no badge field, so surfacing it is a
    contract addition. §10.12.
18. **Eligibility progress is clamped monotonically.** `EligibilityMachine`
    requires non-decreasing progress; an estimate can jitter backwards by
    centimetres. The clamp is counted (`_eligibility_clamps`, exported) rather
    than hidden, but a genuine progress regression would be absorbed by it.

## 10. Required integration actions

1. **A03 (simulation) — add an electrical-power channel to `Observation`.**
   `simulator_mapping()` already maps `electrical_power_w` and the simulator
   already holds `battery_out_power_w` / `deploy_power_dc_w` /
   `harvest_power_dc_w` on `CarState`. Adding the DC-bus power to `OWN_CHANNELS`
   would let A05 integrate energy instead of holding it, which is the largest
   single quality gap in the loop today (§9.1). Adding `recharge_ledger_j`
   similarly would give the checker a real per-lap ledger (§9.2).
2. **Coordinator — decide what happens to `operator_action` outbox rows.**
   Either add an `OPERATOR_ACTION` member to `StreamEventType` with a payload
   type, or stop writing an outbox row for that event in
   `apply_operator_action`. Both are contracts/persistence changes, so neither
   was made here.
3. **Coordinator — add the discriminator to two outbox payloads.** In
   `db/repository.py`, `store_decision` and `record_execution` should include
   `"event_type": ...` in the payload dict they pass to `append_event`, as
   `_transition` already does. That removes the publisher's repair path.
4. **A04 (rules) — two questions.** (a) Should
   `_check_overtake_eligibility` return `PASS` for a plan that requests no
   `OVERTAKE` segment even when `context.eligibility is UNKNOWN`? Today it
   returns `UNKNOWN` first, which suppresses all advice (§9.3). (b)
   `synthetic-pack-v1` declares detection and activation lines but no gap
   threshold and does not list one as an unknown condition. Either the pack
   should declare a threshold, or it should list
   `overtake_gap_threshold_from_unresolved_event_document` the way
   `synthetic-pack-unknown` does. This module currently supplies the threshold as
   a declared session policy (§8.1).
5. **A06 (planning) — the adapter is deliberately incomplete.** A06's handoff
   landed while this module was being written. `_ExternalPlannerAdapter` calls
   `plan(estimate, rule_context, None, deadline_s, manifest=..., now_s=...)`,
   which matches A06's published signature, but three of A06's own integration
   requirements are **not** implemented and must be before its planner is made
   the default:
   (a) call `build_recommendation(result, estimate, rule_context, ...)` instead
   of the runtime building its own `Recommendation`, and treat a `None` return
   as "keep the instruction in force";
   (b) persist `active_plan_from(...)` and pass it back as `current_plan` on the
   next invocation, without which A06's hysteresis and invalidation cannot work;
   (c) publish `scenario_count`, `candidate_count`,
   `ProbabilityStatement.sample_count` and `calibration_status` alongside every
   probability. The runtime currently publishes `scenario_count=0` and no
   probabilities because `BaselinePlanner` performs no scenario rollout.
   A06 must also confirm that `PlanningResult.state_revision` is set to the
   revision the request carried; the runtime discards results whose revision
   disagrees.
6. **Coordinator — apply `handoffs/A08-integration-patch.md`** to `main.py`
   (three hunks: imports, lifespan wiring, routers). Without it `POST /sessions`
   continues to answer 503 for `session_factory` and the two new route modules
   are not mounted.
7. **A09 (frontend) — `DeduplicatingConsumer` in `session/publisher.py` is the
   reference stream reducer rule.** Delivery is at least once; deduplicate on
   `(session_id, sequence)`. A `resync_required` envelope carries
   `earliest_available_sequence`, which is the cursor to resync from.
8. **A05 (estimation) — the energy gain question.** With a 15 kJ measurement
   sigma and no power channel the energy posterior converges with a ~4 s time
   constant (§9.1). If a power channel is added, please confirm whether
   `energy_sigma_j` still wants to be 15 kJ for a simulator source whose energy
   channel is quantised to 400 J.
9. **Coordinator / A02 — replace `MemorySink`.** The runtime constructs
   `IngestionPipeline(..., sink=MemorySink())`. Point it at
   `TelemetryRecorder(paths.artifacts / "telemetry", session_id, ...)` and decide
   who owns `chunk_duration_s` and the per-source `reorder_window_s` (currently
   0.0 for the simulator, which is correct for an in-order source but is a
   constructor argument with no config file). §9.15.
10. **Coordinator — telemetry gap detection on the stream.** Because the two
    sequence spaces are separate (§9.16), a client sees lifecycle sequence
    continuity but has no equivalent for telemetry. If that matters, a
    `telemetry_view` payload should carry the ingestion sequence range in its
    existing `coalesced_from_sequence` / `coalesced_to_sequence` fields, which
    this module does not yet populate because it does not publish telemetry
    views.
11. **A09 / coordinator — the session badge.** `badge_for()` exists in A02 but
    `SessionSnapshot` has nowhere to put it. Either add a field or let the
    frontend derive the badge from `manifest.mode` plus `manifest.synthetic`.
12. **A13 (evaluation) — `runtime.export_record()` and
   `routes/exports.build_export_body()`** are the two complete-record shapes. The
   second is the auditable one (it reads the store, not the runtime's memory) and
   carries manifest, hashes, decisions, operator commands, lifecycle transitions,
   execution events, session events, outcome records, telemetry chunk references,
   software versions and a units map.

## 11. Fixture and source provenance

Every scenario, track, car, rule pack, objective and model manifest used by this
module and its tests is a synthetic fixture already in the repository
(`configs/scenarios/`, `configs/tracks/`, `configs/cars/`, `configs/rules/`,
`configs/objectives/`), authored by A03/A04 and declared
`verification: synthetic_assumption`. The `ModelManifest` objects in
`test_degradation.py` are constructed in the test with obviously fake hashes and
describe no trained model. The credential strings scanned for in the export test
are absent by construction, not redacted from anything real. No external dataset,
no licensed feed, no third-party code and no network call appears anywhere in
this module or its tests. Dependencies used are the ones the coordinator already
locked: pydantic, SQLAlchemy, FastAPI, numpy (transitively, through the core
packages), PyYAML.
