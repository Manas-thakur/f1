### The learned continuation protocol (A07)

```python
@runtime_checkable
class ContinuationModel(Protocol):
    @property
    def bundle_id(self) -> str: ...
    def in_support(self, features: Mapping[str, float]) -> bool: ...
    def continuation_value(self, features: Mapping[str, float]) -> tuple[float, float]:
```

Features supplied per rolled-out scenario: `own_energy_j`, `horizon_s`,

## 3. How it works, and the choices that are arguable

### Control representation

Control is a short sequence of driver-selectable `ProfileSegment`s over a
corridor, each with a continuous energy allocation. No millisecond power trace is
ever emitted. The instruction lead time (1.0 s) and the execution window (1.5 s,
never longer than the segment) live in the frame; a corridor no human could
execute is suppressed before optimisation, not downgraded. Only the head segment
is executed; the rest exists so the head is decided against a horizon containing
its consequences.

### Agreement with the independent checker

The frame reproduces the reintegration model A04 declares, so the two disagree
only where they genuinely disagree. The frame holds one speed across the
corridor, matching a single-sample *step* `SpeedProfile`, under which the
checker's trapezoid is exact, `ceiling_integral = C_reg(v)·dt` and deployment
power is constant at `requested_budget_j / dt`.

`checker_state_for` accepts a `speed_profile`. When the caller supplies a real
forecast the checker reintegrates along it while the planner's coarse frame does
not — which is exactly the situation in which a converged solve is rightly
rejected, and is how `test_constraints.py::test_solver_success_with_checker_failure_is_not_accepted`
is constructed rather than by faking a verdict.

### The smooth surrogate (`surrogate.py`)

Written once in ordinary arithmetic with `exp`/`log` injected, so the CasADi
formulation and the Python evaluation used for scoring and testing are the same
function. Over a segment of length `L` at held speed `v`, with `e` joules out of
the battery and `h` joules of battery gain:

```
u   = eta_drive * e - zeta * h / eta_charge          net propulsive energy
t   = L * (v^3 + beta * u)^(-1/3),  beta = v / (k L) cubic-drag settling
E_T = E0 + sum(h) - sum(e)                           battery ledger, D-01
```

`zeta` (0.35) is the harvest opportunity coefficient: the share of recovered
mechanical energy that would otherwise have driven the car. It is the single
largest source of surrogate/simulator disagreement and is declared as such in the
config.

Loss per scenario:

```
loss_w = w_time * t
       + w_pos * sigmoid(-advantage_w / tau)
       - v_rate * E_T
advantage_w = advantage_0 + (t_baseline - t) - pace_w
            - counter_rate * softplus((reserve_w - E_T)/scale) * scale
```

* `v_rate = gamma^H * w_time * eta_drive/(3 k v_ref^3) * availability` — the
  marginal rate a stored joule buys time at, discounted, and tapered to **exactly
  zero** at the true finish. It is a rate, not a fixed reserve, so nothing rewards
  arriving at the flag with a full battery.
* The counterattack term is what makes a greedy pass lose the place again inside
  the modelled horizon.
* `w_pos` and `counter_rate` are set to zero when no rival is believed to be in
  contention, because then there is no position to win or lose.

The objective adds `lambda_tail * (eta + sum p_w xi_w / (1-alpha))` with
`xi_w >= loss_w - eta`, `xi_w >= 0`, and `lambda_switch * switch_count`. `alpha`,
`lambda_tail`, `lambda_switch`, `minimum_dwell_s` and `improvement_threshold` all
come from the frozen manifest; none is defaulted.

### Solver

CasADi/IPOPT (`decisions.md` D-02); the identity is recorded on every candidate's
`solver_status`. One compiled `nlpsol` per `(segments, scenarios)` shape, cached
process-wide, with every datum a symbolic parameter — so a candidate costs a
solve, not a code generation.

Energies are scaled to megajoules inside the solver and every constraint row is
normalised to order one. This is load-bearing: a joule is worth about `1e-6`
utility units, so the unscaled formulation puts the entire gradient below IPOPT's
convergence tolerance and *any feasible point looks optimal*. The first
implementation had exactly that defect and the hand-computed test caught it —
the solver returned the deployment bound instead of the closed-form optimum.

Near-term control is a single shared `(e, h)` vector evaluated in every scenario,
so non-anticipativity is structural rather than a constraint that could be
forgotten.

### The hand-computed allocation

With no rival the loss reduces to the time/energy trade, and the stationary point
has a closed form the test derives from scratch:

```
dL/de = 0   =>   v^3 + b e = v^3 * (gamma^H * availability)^(-3/4)
e*        =      v^3 * ((gamma^H * availability)^(-3/4) - 1) / b,   b = eta_drive v / (k L)
```

The segment length cancels and so does `w_time`, which is the check that it is a
physical trade and not an artefact of the objective's scale. For 300 m at
75 m/s, `k = 0.6` kg/m, `eta_drive = 0.95`, `gamma^4 = 0.986755`, availability
0.8: `b = 0.3958333`, `(0.986755 × 0.8)^(-3/4) = 1.1940610`, and
**`e* = 421875 × 0.1940610 / 0.3958333 = 206 825 J`**. The solver returns it to
`1.9e-8` relative; the test asserts `1e-5`, roughly three decades above IPOPT's
own `1e-8` convergence criterion.

### Two tests whose stated premise turned out to be wrong

Both are recorded here because the conclusion matters more than the test.

**1. "A greedy pass scores better on a truncated horizon."** It does not, and the
first version of the test asserted that it did (greedy 14.47 against reserved
13.81 — the coordinator's re-run caught it). The reason is a property of the
model, not a bug: the continuation value and the counterattack response attach to
the **end of whatever corridor is scored**, so truncating the frame moves the
accounting with it instead of dropping it. There is no horizon at which this
surrogate credits a pass as permanent progress.

The test was rewritten to compare *scoring rules* rather than horizons, which is
what the specification actually asks for. The naive rule — bank the position won
at the near checkpoint, count neither the energy it cost nor the counterattack it
invites — is now constructed explicitly by zeroing `energy_value_rate` and
`counterattack_rate_s_per_j`, and under it greedy wins 11.86 to 15.21. Under the
planner's real rule over the full defined horizon greedy loses 19.60 to 17.60.
The two rules disagree about the ordering, which is the property under test. A
second test asserts the truncation result directly, so the behaviour is pinned
rather than left as a footnote.

**2. "A plan that uses strictly more energy for no benefit."** With everything
else held equal this is not constructible in this surrogate — any extra
deployment produces *some* time gain, and pairing extra deploy with offsetting
harvest leaves the total requested budget unchanged. That is itself a statement
about the model: it has no waste channel. The dominance case is therefore
asserted where waste is representable — spending past the stationary point,
where the extra joules buy strictly less time than they cost, with the
diminishing-returns mechanism asserted alongside the ordering — and again at the
outcome level, where two re-simulated candidates with identical time and position
are separated only by what is left in the battery.

## 5. Assumptions

1. **`discharge_efficiency = 1.0` in the checker state.** D-01 and the merged
   checker disagree about which bus `requested_budget_j` sits on. The planner
   emits battery-side energy per D-01 and pins the checker's discharge efficiency
   to 1.0, which makes its battery ledger exactly the D-01 quantity and its
   ceiling comparison conservative. See `handoffs/A06-contract-proposal.md` P-01.
   `charge_bus_efficiency` *is* set to the car's real charge efficiency, because
   the harvest side is unambiguous.
2. **Held speed across the corridor.** The frame does not model the speed profile
   the car will actually drive. It is the same simplification the checker makes
   when no forecast is supplied, and it is why supplying a real `speed_profile`
   can legitimately reject a converged plan.
3. **Profile realism bounds.** Deployment is capped at
   `DEPLOY_FRACTION[profile] × ceiling × dt` and harvest at
   `HARVEST_FRACTION[profile] × regen_availability × …`, both taken from A03's
   engine, so an instruction cannot carry a budget the named profile would not
   execute.
4. **Battery window enforced by a conservative interior envelope**
   (`E_i - e_i >= floor`, `E_i + h_i <= ceiling`) rather than by locating the
   true interior extremum. Conservative in the right direction; it can reject a
   feasible plan, never accept an infeasible one.
5. **`SOLVER_HEADROOM = 1e-4`** relative headroom below every hard bound, and
   published budgets rounded to whole joules. Both absorb IPOPT's bound
   relaxation so a zero-margin pass cannot become a small negative fail. Neither
   is large enough to mask a real infeasibility.
6. **`position_persistence = 0.5`** attributes half the finish-position penalty
   to a position held at the end of the detailed horizon. Unvalidated; it exists
   to stop an intermediate position being priced as a finish position.
7. **The rival-energy interval is widened by 1.32** before being used as scenario
   support — see §7.
8. **Rollout world.** Re-simulation defaults to the synthetic
   `two-straight-counterattack` bundle. A caller running a different session must
   pass its own `PlanningWorld`; the planner does not infer one from the estimate.
9. **`ahead_at(checkpoint)`** is defined as our car crossing the checkpoint line
   strictly before the rival crosses the same line (or the rival not reaching it
   inside the horizon). Evaluated at common progress, never by dividing a gap by
   a speed.

## 6. Performance — measured, and the target missed

**Hardware:** Windows 11 (10.0.26200), Intel64 Family 6 Model 183 Stepping 1
(Intel Core Ultra class laptop), CPython 3.12.14, CasADi 3.8.0 with bundled
IPOPT. Not a server, not a fixed-clock machine.

**Configuration measured:** 5 candidates enumerated, 6 scenarios optimised
against, 2 finalists re-simulated across 3 scenarios each (6 simulator branches),
0.5 s re-simulation step over a 10.5 s rollout horizon, 9.0 s detailed horizon.
2 accepted, 3 rejected.

### What dominates

**Two things, and they must not be conflated.**

**(a) The host's clock, over the 40-invocation window.** An independent
arithmetic reference loop, timed in the same process and touching none of the
planner's code, slowed from **42.7 ms to 179.3 ms — a factor of 4.2 — across the
same window**. The machine drops to roughly a quarter of its clock rate under
sustained load. The first ten invocations, taken while the reference loop still
read 43 ms, gave **p95 = 169 ms, which meets the target**, and the fastest
invocation of the whole run was 154 ms.

Running the same test after the rest of the suite confirms it from the other
direction: the host is already throttled at the start, the reference reads
169.6 → 179.2 ms (1.06×, i.e. no further degradation), and the *minimum* rises
from 154 ms to 737 ms while p95 stays at 815 ms.

So: **on unloaded hardware the planner meets the budget; over a sustained
40-invocation burst on this laptop it does not, and roughly a factor of four of
that is the host.** A fixed-clock machine is required before this number can be
quoted as a planner figure, and it must never be quoted as an acados figure
(`decisions.md` D-02).

**(b) Re-simulation, inside the planner.** Measured directly in a fresh process:

```
no rollout (enumerate + 5 IPOPT solves + 5 independent checks): p50=21.6  p95=25.8 ms
with rollout (6 simulator branches):                            p50=159.3 p95=167.1 ms
                                     re-simulation share of p50: 86%
```

Enumeration, five continuous solves and five independent checks together cost
about 22 ms. Everything else is the full-physics re-simulation, and inside that
the simulator's braking-preview `_envelope_speed` dominates. The bounded budgets
(finalists × scenarios × steps) are the only lever the planner has, and every one
of them is published with the decision so a lower resolution can never be
presented as the same confidence level.

### What the latency test asserts, and why not the target

The test **records** p50 and p95 and prints an explicit `TARGET MISSED` line; it
does not assert them. Two absolute assertions were tried and both rejected:

* a fixed `p95 <= 200 ms` ceiling passes in a fresh process and fails when the
  same code runs after the rest of the suite. That is a flake reporting on the
  host, not a regression guard on the planner;
* normalising by the CPU reference does not rescue it either, because the host
  changes speed *during* the measurement window, so no single factor describes
  the run.

What it does assert is hardware-independent: the bounded work the planner
declares (candidate, scenario and rollout counts), a 20× smoke ceiling that
catches an algorithmic regression, and — in the second test — that under the real
200 ms budget every result is either `ok` within the budget or
`deadline_exceeded` with nothing published. A slow host produces more
`deadline_exceeded`, never a late `ok`. That is the property that matters
operationally and it holds regardless of clock speed.

## 7. A05 integration — what was honoured

1. **Energy gating.** `_verify_inputs` gates on **both**
   `estimate.quality.own_energy_capability` (A05's session-level declaration) and
   `own_car.has_energy_capability`. Either being false returns
   `INPUT_UNAVAILABLE` with `OWN_ENERGY_UNAVAILABLE` and withdraws advice. Two
   tests cover it, including the case where a value is present but the
   session-level flag is false.
2. **The rival energy interval is treated as optimistic at its own label.** A05
   measures 0.7885 empirical coverage against a nominal 90 % label on 156 records
   and attributes the shortfall to bias, not spread. The planner widens the
   half-width of a `quantile`/`confidence_interval` belief by
   `interval_coverage_widening = 1.32` before using it as scenario support —
   `z(0.95)/z(0.89425) = 1.6449/1.2485 = 1.317` under a Gaussian re-scaling. The
   config entry says in full that this is a **conservative margin, not a
   correction**: A05's bias is not fixed by widening and the disclosed coverage of
   the underlying belief is unchanged.
   A `physical_bounds` range is *not* widened — it is a support, not a
   statistical statement — and it now carries `RIVAL_ENERGY_UNKNOWN`, because a
   range spanning the whole battery identifies nothing.
   `ScenarioSample.energy_support` records how the nodes were derived and is
   written into `PlanningResult.detail`, so a decision record can never present a
   widened optimistic interval as a calibrated bound.
3. **Protocol compatibility verified at runtime**, not assumed — see §2.

## 8. Known limitations and remaining defects

1. **The latency target is not met over a sustained burst on this hardware.** §6.
   Needs a fixed-clock machine to be measured properly, and re-simulation is 86 %
   of the planner's own cost.
2. **`requested_budget_j` bus ambiguity** — `A06-contract-proposal.md` P-01. The
   workaround is safe but an integrator setting a realistic `discharge_efficiency`
   today gets an over-drained checker ledger.
3. **Only the terminal point of each sampled trajectory is used.** A05's
   trajectories carry a full correlated energy and pace path; the planner reduces
   each to a terminal reserve plus a final mode. The correlation structure A05
   went to some trouble to produce is therefore not yet exploited, and
   `reachable_energy_step_j` is not consulted.
4. **`harvest_opportunity_coefficient` is unvalidated** and is the largest source
   of surrogate/simulator disagreement. Nothing has measured it.
5. **Deploy and harvest are bounded independently within a segment**, so a
   schedule can request both near their bounds in one instruction. The bounds are
   physical (regen availability, profile fraction) so this is not unbounded, but
   there is no duty-cycle constraint tying the two together and one may be needed.
6. **Torque limiting is not modelled** anywhere in the constraint set — the
   thermal envelope is, the torque envelope is not. Inherited from the rules
   module's coverage matrix, and the planner does not add it.
7. **No geometric contact likelihood.** Lateral geometry is not resolvable from
   the fixtures, so no contact-risk probability is produced. `pass_before` and
   `ahead_at` are longitudinal and checkpoint-based only.
8. **`ahead_at` uses a two-car field.** With more rivals, "crossed the line first"

10. **Interior battery extrema are bounded conservatively**, not solved for

11. **acados is not used.** CasADi/IPOPT figures must not be quoted as acados
